# レビュー判断の基準

コード・仕様・実行証拠から、指摘の成立条件、影響、PR の目的との関係を判断する。reviewer の解法は候補であり要件ではない。証拠確認と修正判断は同じ担当が行ってよい。

優先度の目安:

- P0: データ破壊、重大な security 問題、主要機能停止などの緊急 blocker。
- P1: マージ前に解決すべき明確な不具合・高影響の回帰・仕様未達。
- P2: 影響と修正コストを比較して今回扱うか判断する問題。
- P3: 任意の改善や follow-up。

好みやテスト件数そのものを欠陥にしない。テストは守る挙動と実際のリスクに合わせ、既存の証拠で十分かを判断する。

症状が事実でも、承認済みの受け入れ範囲なら修正が必要とは限らない。正本仕様と承認の所在を確認する。詳細は `$AA_AGENT_DIR/knowledge/human-approval-policy.md`。

多数の指摘で追跡が難しければ台帳、cluster、batch を使う。出典と未処理範囲を失わなければ、固定件数や二重の採否台帳は必要ない。重要な未確認を完了へ丸めない。

横断的な設計判断には `integrated-fix-planning` が使える。領域固有の証拠を調べるときは `$AA_AGENT_DIR/knowledge/review-reference/domain-evidence.md` を関連箇所だけ参照する。
