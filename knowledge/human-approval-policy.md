# 操作権限と人間判断

ユーザーの依頼と既存承認を先に確認する。承認済みの範囲について再確認を求めない。技術名、module 数、計画との差異だけで停止せず、新しい権限や人間だけが決められる選択が必要かを判断する。

## Steward の裁量

- 対象 PR のレビュー、必要な検証、承認済みの目的・挙動を満たす修正。
- 既存仕様から正解が決まる UI 修正、実装上の調整、計画の訂正。同期手段や内部構造の選択も含む。
- 指定 PR head への検証済み通常 push。`pr-push-safety` の安全条件を確認する。
- レビューと必要な修正・検証が完了した対象 PR への `pr-steward` ラベル付与。ラベルが存在しない場合の作成も含み、都度確認は不要。

## 追加の承認が必要な境界

既存の依頼・承認に含まれない、次の変更・操作は具体的な結果と影響を示して人間へ返す。

- 製品の挙動、重要な UX、公開 API 契約、互換性や提供範囲についての新しい選択。
- DB migration、認証・認可、課金、データ削除の新しい設計判断・操作。承認された設計内の実装作業には再承認を求めない。
- 対象外の branch / repository への書き込み、base / target branch の変更、maintainer 以外の branch への push。
- PR の merge、close、approve、request changes、他者へのメッセージ投稿。

規模や複数領域に触れること自体は承認事項ではない。目的外の拡張や、既存仕様から決められない tradeoff があれば判断を求める。文脈不足はまず参照・調査で解消し、必要な情報が人間にしかない場合に質問する。

## 保護する操作境界

- user changes を破棄・上書きしない。force push、rebase、history rewrite は Steward の実行対象外。
- secret / credential / token / private key らしき差分は値を表示・保存・公開コメントしない。該当部分の公開・push を止め、値を伏せて対応を人間に求める。自動 reject の理由として公開しない。
- GitHub 認証・権限の修復は member に任せる。agent が credential を選択・作成・差し替えない。

## 明示された merge 依頼

対象 PR の「マージして」は、最新 base との互換な意図を保持する最小限の conflict 解消、必要な検証、通常 push、通常 merge を含む。conflict だけを理由に再承認を求めない。

どちらかの仕様を捨てる、新しい契約・権限・データ変更が必要、または目的外へ拡大する場合は判断を返す。remote 更新を確認し、他者の変更を失わない。Git 操作は `$AA_AGENT_DIR/knowledge/github-pr-operations.md` を参照する。

## 承認済みの副作用

PR が受け入れ済みの挙動を主張する場合、正本 SPEC、変更境界、実際の承認を照合する。status の文字列だけで承認を判断しない。受け入れ済みなら症状が事実でも merge blocker にせず、再検討が必要なら仕様 owner へ返す。

計画に誤りがあっても、承認された目的と境界内で訂正できれば続行する。修正不要という結論も有効。新たな判断が必要なときだけ、選択肢とユーザーへの影響を簡潔に示す。
