# approved plan の「推奨する形」は十分条件ではない。既存 test が固定した契約が勝つ

## 発生した問題（抽象化）

approved fix plan が、ある関数の置き換え形として具体的な API 形状を「推奨する形」として書いていた（全世代を新しい順に列挙して返す）。そのとおりに実装すると、列挙の途中で現行世代の描画が上限超過で失敗し、列挙全体が失敗する。結果として、既存 test が固定していた「現行世代が上限を超える historical な入力でも、受理済み世代なら復元できる」という契約が壊れた。

plan が同じ節で述べていた十分条件（保存済み hash に一致する世代を選び、無ければ integrity error を返す）は、別の形でも満たせた。推奨形をそのまま採ると、plan 自身の十分条件は満たすのに、plan が触れていない既存契約を壊す。

## 再発防止（How to apply）

1. plan の記述を「十分な解決状態」と「推奨する形」に読み分ける。前者が承認された要件、後者は planner の一案である。両者が衝突したら前者を採り、採らなかった理由を audit record に書く。
2. 関数やモジュールを置き換える前に、その関数を呼んでいる既存 test を読む。特に「失敗する入力」「境界ちょうどの入力」を扱う test は、置き換え形が壊しやすい契約を持っている。
3. 置き換え形を選ぶ基準は「plan の十分条件を満たし、かつ既存の pinned 契約を全て保つ最小の形」。plan の文面への忠実さではない。
4. 逸脱したら、どの契約を守るために逸脱したかを、その契約を固定している test 名とともに記録する。plan からの逸脱と、無断の設計変更を区別できる形にする。
